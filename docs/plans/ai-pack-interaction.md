## 目标与范围

让玩家从角色、物品、场景或规则对象发起有明确来源的需求，让 KP 在同一工作区讨论方案、核对影响并分别批准与加载。服务商和密钥留在独立本机管理器；包侧只接房间身份和授权数据。

已交付可操作原型：启动 AI 管理器后点击左下角“配置包交互原型”，或访问同一服务的 `/prototype.html`。原型使用真实 `mountChat` 组件及固定内存 Transport，页面明确标记“演示数据 · 不连接游戏”。可切换 KP／PL，体验旅行提灯的引用、方案、A/B/C、风险确认和分步批准/加载。所有数值与检查结论均是交互演示，不是树桩镇规则或检查引擎的验收结果。[界面截图](../../engineering/acceptance/ai-runtime/chat-pack-prototype.png)和[浏览器验收](../../engineering/acceptance/ai-runtime/chat-browser.json)记录了实际操作。

2026-11-14 原型与通用组件已补齐指令名称补全及语义引用标签；最新效果见[语义引用截图](../../engineering/acceptance/ai-runtime/reference-ui-semantic.png)。这部分交互已实现，以下正式包侧接线和玩法验证仍按阶段推进。

2026-11-14 通用工程进一步交付单独页面、对话页面、可折叠面板及无界面装配工具。三个版本与同源 HTML 入口的现有行为由[配置包嵌入指南](../current/engineering/ai-pack-embedding.md)维护；本计划中的正式包侧接线和玩法验收仍待各包推进，不因通用组件完成而自动完成。

## 布局与操作

| 区域 | 呈现内容 | 操作 |
| --- | --- | --- |
| 游戏对象区 | 当前场景、角色、背包、规则入口与当前会话列表 | 对可访问对象点击“带入 AI 讨论”，插入带修订的引用；不默认发送 |
| 对话区 | 当前房间/会话、需求、方案说明、状态、底部输入与引用预览 | 文本输入，或 `/config`、`/entity`、`/data` 补全；发送后显示队列/生成/检查状态 |
| KP 审核区 | 候选配置差异、影响对象、A/B/C 证据、风险理由及当前修订 | A/B 阻断时改稿；C 缺证据明确 unknown；批准本修订后，单独加载 |

桌面建议三栏；窄屏保留游戏主视图，将 AI 作为抽屉，审核作为独立详情页。原型已有窄屏顺序布局，尚不替代包侧正式布局验收。对象名称、状态和报错须接包的本地化模块；当前通用组件文案仍以中文为主。

PL 只提交自己的需求和查看状态，原型不向 PL 展示审核区或调用按钮。当前服务并不自动把包含 KP 上下文的模型回答公开给玩家。若需要“KP 将选定答复公开给 PL”，须新增明确的发布投影与来源审查，不能直接共享 KP 会话或复制完整响应。

KP 自己的会话可在点击发送后转交 AI；玩家需求继续经房间队列由 KP 明确转交。已有自动接收功能只适用于 KP 配置的获授权频道/前缀，包侧不得把全部聊天默认交给模型。取消需求不回滚已经加载的游戏变更。

## 引用与异常交互

1. 输入 `/` 或 `/en` 等前缀先补全指令本身，选择指令后再补全对应对象；点击对象也可带入。候选以当前账号可访问的数据名称及可见范围呈现。`/data` 仅 KP 可用，指当前活动工件的 JSON 数据文件，不是任意磁盘文件。
2. 选择后插入有底色、加粗的“旅行提灯”等语义标签；输入和消息显示可读名称，底层保留 `[[entity:对象ID@修订]]`。标签整块增删、剪切和替换，支持撤销/重做，不能留下半截引用。普通文本复制得到名称，组件间粘贴可保留引用身份。实际数据由宿主解析；前端传来的名称、内容或账号不能成为权威数据。
3. “查看引用”显示此次将引用的只读值；正式调用还受房间公开/KP/私密外发策略限制。预览成功不代表已批准外发。
4. 来源过期时提示重新选择；不得把旧标记自动换成最新修订并继续发布。撤权或不可访问时隐藏正文；换房、换账号、卸载面板须清理草稿、候选列表与迟到响应。
5. 生成失败保留已提交需求及状态；提交结果未知时使用原请求 ID 查询回执。批准绑定本次候选修订，改稿须重新检查和批准。

当前通用接口已经支持配置、活动实体和活动工件数据引用。包侧的场景状态、笔记、聊天及 `package.json` 尚不能直接当作这些引用：需先实现有版本和权限的来源适配，或明确投影为宿主已支持的数据。

## 接入层级与实施步骤

| 阶段 | 工作与负责方 | 验收条件 |
| --- | --- | --- |
| P0 原型评审 | KP、玩家和包作者确认入口、术语、对象动作及审核布局 | 从游戏对象进入讨论，无需手工找 ID；PL 不能看到 KP-only 面板。现有原型供评审，不代表已获用户体验反馈 |
| P1 咨询接线 | 包作者通过公开 `pack.js` 和 `AiClient` 或自定义 Transport，选用三种视图之一，或装配 `createAITools`、`mountChat`、`bindReferenceInput`；按真实身份配置路由白名单 | 新建/归档/续聊、引用、权限撤回、断线与换房清理通过；无需复制服务商面板 |
| P2 首个配置范围 | 包作者定义可改字段与消费路径；工程提供 A/B/C 执行、作者提供规则及场景 | 实际需求→生成→三检→改稿→批准→加载→游戏中消费；已有实例与无关文件保持原语义，重复提交不重复生效 |
| P3 包侧来源 | 工程提供受信来源适配，包作者定义场景/笔记等数据修订与可见性 | 提交、外发、读回、审核与加载复验；对象删除/编辑、撤权和恢复分叉均使旧依据失效 |
| P4 多人试玩 | 包作者、KP 与 PL 验证布局、本地化、时延及跨设备传输 | 一名 KP、两名 PL；独立身份、窄屏、取消/超时/重启/过期；保存玩法反馈与验收证据 |

开发者可直接使用 `/api/v1/ai/references`、`references/resolve` 及会话/命令 API，自制对象选择器和聊天界面。更底层 Python `References` 只处理已可信的账号与宿主，不应直接暴露给未经鉴权的网络输入。嵌入示例、配额和生命周期见[当前接口文档](../current/engineering/ai-manager.md)。

## Stumpsville 对应方式

树桩镇现有 AI 咨询与网页个人会话已接通，本原型不重写已上线流程。可先将其顶栏 AI 助手或 PL 需求入口接到 `mountChat`，从角色/库存对象动作插入引用，保留当前地图、日志与聊天布局。新增引用路由和组件静态资源仍须在包代理及网页服务桥中分别增加最小白名单并验收；通用宿主支持新 API 不代表包桥自动开放。

旅行提灯只是首个“受限物品模板”的候选。真实实施前需明确库存和生成动作从哪个运行目录读取模板，包作者提供字段限制、A/B/C 场景与指标；不得仅生成 JSON 就宣称物品已进入背包。批准与加载只覆盖宿主原子事务，包侧存档更新须另行设计。详细前置条件继续由[树桩镇接入计划](stumpsville-ai-integration.md)维护。

## 待确认问题

- 正式首个配置闭环是否选择受限物品模板，以及具体字段与可接受的玩法影响。
- KP 更倾向常驻右栏还是按需审核抽屉；是否需要另行设计安全的“答复玩家”功能。
- 哪些包侧数据允许外发、谁维护其修订与授权；真实跨设备试玩安排。

这些问题不阻塞已交付的管理器、通用组件和只读引用服务。后续按阶段登记施工、实现、验收并同步文档。
