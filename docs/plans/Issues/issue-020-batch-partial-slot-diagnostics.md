## 现象与证据

用户于2026-11-20提供“执行结果与定位”截图，显示AI行动“部分完成”，但只有状态和定位JSON，没有逐项结果或停止原因。本次仅核查现有记录与代码，没有运行新命令或修改正式存档。

截图批次共有3项：使用物品、短休、向原玩家通知。唯一回执是第1项`action.invoke / sv.inventory`的明确拒绝`RULE_FAILED`，第2、3项未尝试。因此这笔实际为成功0项、失败1项、未执行2项。

生成摘要声称第3槽为口粮且有3次用量；实际提交`operation=use, slot=3`。回执所用工件和执行前后状态显示：第3槽的物品编号为6，对应整轮奶酪，定义和当前用量均为0；口粮的物品编号为3，实际放在第5槽，有3次用量。房间代际101与102的目标角色对象逐字段相同，HP保持2/4，口粮未消耗。仅保留必要事实，不将整份真实对话或存档复制入问题文档。

## 施工前确认的原因与当时验证边界

- [批次执行器](../../../engineering/ai/src/onlinecoc_ai/batches.py)在任意动作明确拒绝时立即将批次标为`partial`并停止后续动作，没有区分此前成功数量。因此`partial`并不保证至少有一项成功；本例界面文案有误导。
- 该候选确实用错背包槽位。把“口粮的物品编号3”当作“所在槽位3”是与现场一致的可能生成原因，尚未通过模型对照实验验证其内部原因。
- 该工件的`sv.inventory.core`不允许对`uses=0`物品调用`use`。现有回执只保存`RULE_FAILED`，未保留内层Lua断言原因；没有隔离重放，因此不将具体断言当作已复现的唯一报错位置。
- 批次按项执行，各项保留回执；不能以统一文案声称全批原子回滚，也不能对真正已成功的前置项盲目重放。本次实际没有成功的前置项。

## 候选处理与分工

1. AI模块／引擎责任者明确零成功失败、真实部分完成、结果未知的状态契约，提供每项成功／拒绝／未执行及安全错误原因；不在前端猜测未返回的回执。
2. 配置包消费逐项结果，消息详情直接显示失败动作、原因和原命令定位；复用历史查看，不修改正式候选或自动补执行。
3. 配置包和AI模块分别评估物品编号与槽位的语义投影、工具输入提示和候选检查；避免仅依赖模型文字承诺“已核对”。新增或改变规则语义另行评估。

## 验收条件

- 首项拒绝显示0成功／1失败／其余未执行，禁止文案暗示已经扣除或回血；第二项拒绝时准确保留第一项成功事实。
- `pending/unknown`保持结果待核对，重启／丢回复沿用原回执，不重放已经成功的动作。
- 覆盖“物品编号3位于槽5，槽3为其他物品”的候选准备；移槽后能依据新资料核对，不能把编号当槽位。
- 错误原因和动作定位可追溯且不泄露KP私密资料；PL通知只在相应前置动作真实成功后发出。
