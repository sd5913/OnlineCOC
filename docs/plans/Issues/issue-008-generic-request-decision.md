## 现象与预期

目前“申请一个行动—由指定主体决定—执行并反馈”分别使用流程等待、包侧字典或规则实体表达。它们能实现玩法，但请求身份、决定、证据、受众和执行记录缺少统一读取与关联格式，UI、聊天、AI 和其他配置包需要逐一解释。

用户于 2026-11-14 要求把“裁决”或“请求”作为一类新的通用数据格式思考并提交 ISSUE。本提案建议定义**通用交互记录**，覆盖请求和决定两种关联语义，成为独立于 AI 的通用业务模型。工程方需评估采用单一记录族还是两个关联模型；以下 `InteractionRequest / DecisionRecord` 是候选名称与表示，不是已确定的接口。

目标是让配置包继续定义检定、伤害、交易和叙事规则，工程统一身份、来源引用、权限、记录生命周期、幂等和执行关联。即使不启用 AI，这些记录也应可持久保存、查询和恢复。

本 ISSUE 不宣称当前引擎无法实现上述玩法，不要求把现有包侧实现立即替换，也不把提出模型设计等同于授权本轮实现。

## 原因与候选处理

### 1. 推荐分层

| 层次 | 责任 |
| --- | --- |
| 文件存储层 | 保存数据和事务，不识别裁决含义 |
| 引擎通用业务层 | 管理请求/决定的身份、权限、版本、关联、幂等及可见投影；提供 HTTP/SDK/进程内契约 |
| 配置包 | 声明请求类型、结构化输入/输出 Schema、合法决定及其业务规则；指定决定如何映射到行动 |
| UI、聊天、AI | 创建获准的请求、展示状态、查询引用、提出建议；使用正式命令提交决定，不自行修改记录成为事实 |

建议先实现稳定契约与受信读取适配，再决定是否将写入及持久化统一纳入宿主。请求/决定不依附 Entity 的角色数值或 AI 私有仓库；既有 Flow、Wait 和命令回执继续负责流程推进与实际执行，避免两套调度和结算系统。

### 2. 候选数据格式

逻辑上分开保存原始申请和对它的决定，以容纳“一次请求、多次讨论或改判”。工程可选择独立集合或单一记录族，但已确认决定不能原地改写后抹去历史。

| 候选模型 | 通用字段及含义 |
| --- | --- |
| `InteractionRequest` | schemaVersion、requestId、roomId、scopeId、revision；发起主体、接收/处理角色；包命名空间下的 type；subjectRefs、结构化 payload、文字说明、sourceRefs；创建时间、截止时间（可选）、状态、可见性 |
| `DecisionRecord` | schemaVersion、decisionId、roomId、scopeId、revision；可选 requestRef（允许主动裁定）；决定主体、确认时间、依据 sourceRefs、包类型及版本；结构化 outcome、reason、适用范围、状态；supersedes、executionRefs、可见性 |
| 共享引用 | 来源类型/命名空间、稳定 ID、来源版本或摘要及所属作用域；聊天、实体、规则、流程、请求、决定和回执均通过显式引用关联，后端验证而非信任前端自报 |

两类记录均需声明 `type` 对应的 Schema/契约版本；包扩展 payload/outcome 按声明验证，不接受任意字段绕过权限。是否有单独 requestRef、scope 的复用方式和主体结构在契约评审中冻结。避免与 AI 模块现有 `Request` 类型同名后混淆“生成任务请求”和“游戏业务请求”。

决定主体可为有效房间成员或受信规则执行过程。自动决定须记录规则修订、触发来源和执行身份；模型文本不能自行标为受信规则或 KP 决定。主体 ID、服务端时间、正式状态和摘要由宿主产生或校验。

### 3. 分开三种状态

| 维度 | 候选表达 | 要避免的混淆 |
| --- | --- | --- |
| 请求生命周期 | draft / open / closed / cancelled / expired | 关闭请求不表示行动成功；具体关闭策略由包契约声明并由后端校验 |
| 决定记录生命周期 | draft / confirmed / superseded / revoked | 拒绝玩家行动仍可是一条 confirmed 的正式决定；不要用 rejected 同时表示两种含义 |
| 决定内容与执行情况 | outcome 表达允许、拒绝、附条件或结构化回答；执行情况由 executionRefs 对应回执派生 | 允许进行检定不等于检定成功；已确认决定不等于已完成执行；没有执行需求可明确表示 |

例如 KP 决定“允许尝试开锁”后，检定可能失败；纯叙事决定可以没有执行回执。改判生成新决定并引用旧决定，撤销不自动恢复已经扣除的资源。持续房规的正式修改仍走规则/配置变更流程，记录一条“长期适用”说明不能直接改写生效契约。

初版不必支持所有候选状态，但冻结的枚举必须有明确转换、权限和错误条件，不能通过随意改状态字符串绕过处理步骤。

### 4. 操作与事务约束

建议评估最小服务集合：创建/提交请求、撤回请求、提交正式决定、替代/撤销决定、按权限查询及关联已验证执行。具体命令名称与路由待工程冻结，统一复用宿主命令封套、版本前置条件和持久回执。

- 创建请求不授予执行权限；明确谁可以回答、决定、改判和关闭。KP 角色也不能借查询读取其无权参与的私聊。
- 同 commandId 重试返回原结果；换 commandId 重复确认或处理同一业务请求，也要依赖请求版本和业务约束防止重复消费。
- 正式决定的记录、请求状态变化和对应审计在同一宿主事务提交。若同一事务内执行规则并产生效果，应有共同提交保证。
- 若决定与执行跨阶段，执行单独引用决定的不可变版本，由业务约束防止重复；中断或响应未知先查原回执，不靠重做行动对账。多步骤部分完成需要明确表示。
- 新决定依赖的当前输入、实体或规则已变化时按包契约拒绝或重新确认。历史决定继续表示“当时作出了什么决定”，与“当前还能否据此执行”分开。
- 已确认记录保留可追溯修订；撤回来源不能回滚已发生的行动，也不能绕过当前权限重新展示旧来源正文。删除/保留策略及恢复作用域由工程明确。

### 5. 查询、权限与 AI 接入

提供按请求类型、主体、状态、对象引用及有界时间/序号范围查询的接口。授权过滤先于检索和分页；引用到的来源逐项复验，读取一个决定不能自动打开整段私聊、隐藏对象或其他账号回执。摘要与导出继承相同权限，不泄露隐藏记录数量。

AI 只读这些记录，将其作为[聊天裁决资料草稿](../ai-data-query-adjudication.md)中的权威来源；该草稿的 EventBundle 继续作为组合读取投影，不成为第二份请求/裁决事实库。AI 生成的建议需通过正常受权决定命令才可成为正式记录，不能由模型调用审批/执行工具自行生效。

当新记录用于配置提案依据时，须接入现有上下文来源、A/B/C 证据和发布前复验。格式声明或前端引用标签不能替代宿主接线；未完成复验的包侧资料仍只限明确标识的咨询。

### 6. 与既有实现的衔接

- 树桩镇先将 requests、receipts、events 通过受信适配映射为候选格式；保持真实原始 ID，缺少裁决者、时间或版本的历史资料明确为未知/不完整。
- 以 ISSUE-003 的协作/结构化问答作为第二类评审样例，验证新类型是否减少特殊映射。无需为论证新模型而重做该包已完成的玩法。
- Flow/Wait 可关联请求与决定；首版没有需求时不扩成通用多人工作流编辑器。正式行动结果继续由命令执行器产生，不接受客户端上传“成功”替代实际回执。
- 若新增持久集合改变 Room 格式，按 [ISSUE-007](../../history/2026-11-14-issue-007-room-version-policy.md) 发布清晰的新旧定义与差异，由配置包作者或数据持有方迁移；不重新引入旧房间自动升级。

## 实施步骤与验收条件

### 阶段建议

1. **模型评审**：工程方比较“单一通用记录族”“请求＋决定两个关联模型”“仅标准读取适配”三种方式，明确落层、成本与取舍；冻结术语、主体、状态和权限矩阵。
2. **契约与样例**：交付 JSON Schema、操作/查询契约及正反样例，覆盖自动判定、KP 裁定、纯叙事回复、拒绝和改判；同步说明与 Entity、Flow/Wait、回执、AI Request 的区别。
3. **读取试点**：复用树桩镇与 ISSUE-003 的既有场景校验映射和来源权限，先证明格式可用，不宣称已完成通用宿主写入。
4. **宿主接线（评审通过后）**：按选定方案实现事务、幂等、权限、版本和恢复；更新发行版本说明，再逐包迁移接入。

### 必须回答的验收问题

| 场景 | 通过条件 |
| --- | --- |
| 纯叙事与规则执行 | 同一格式能表达“只有正式回答”和“允许检定后失败”，不将二者误标为同一成功状态 |
| 角色与来源 | 玩家只能操作授权请求；伪造 KP、规则主体、聊天引用或他人回执均失败；私密投影正确 |
| 幂等与并发 | 同 ID 重试、不同 ID 重复处理、两名 KP 同时处理和响应丢失均不重复消费；过期修订拒绝 |
| 改判与撤回 | 新旧决定可追溯；旧决定不会因字段覆盖消失；撤销不暗中重掷或回滚已生效游戏状态 |
| 断点与恢复 | 能区分决定已确认、执行未完成、部分完成及结果未知；重启使用回执恢复，不重复执行 |
| 跨包表达 | 树桩镇的行动申请及另一类结构化问答/协作样例可使用共同契约，包规则仍独立 |
| AI 与非 AI | AI 未启用时记录仍可创建/查询；模型建议不能自行确认；有来源版本的 AI 查询与失效检查成立 |
| 版本与迁移 | 新 Room 格式及对应契约有发行说明；旧数据缺字段不伪造历史；迁移责任遵循 ISSUE-007 |

以上为拟议验收条件，本次没有执行这些验收。复杂表决、多方审批编排、自动纠正历史状态以及改造所有配置包不作为首版前提。

## 工程回复（2026-11-14）

方向合适，采用“请求＋决定”作为目标模型，不新增 Entity 类型或第二套执行器。三种方案比较、最小状态、权限矩阵、来源完整性、事务与恢复边界及 I0—I3 施工顺序已整理到[工程评估与分期方案](../interaction-records.md)。

本次调整为设计层面的收敛：建议先验证树桩镇与 ISSUE-003 两类读取映射，再冻结写入契约。原因是原始资料缺少部分裁决身份、版本和来源，直接写入通用权威集合会把缺失信息固化。本轮没有实现 requests/decisions 持久集合、HTTP/SDK 或 AI 裁决工具；这些不能标为已完成。后续通用 scope 和持久集合将另行提升 Room 版本，不混入本次 v3。
