## 1. 目标、范围与当前状态

目标是交付可脱离 OnlineCOC 和具体配置包运行的本地化工具，形成“新建项目 → 英文原文 → 中文翻译 → 查改／审校 → 校验／预览 → 独立资源发布 → 使用方加载”的完整闭环。

2026-11-12 已开始实施：**L10N-0 进行中，E0-1、E0-3、E0-4 通过，E0-2 原生目录最终确认未完成；L10N-1～6 未开始**。当前真实能力与证据见[工具工程入口](../current/engineering/localization.md)及[验收记录](../../tools/localization/docs/acceptance.md)。其余路径、命令和性能目标仍为计划，不能视为已有实现。首版范围包含 GUI、CLI、文件协作、基本引用与导入导出、独立解析库和 Windows x64 发行物；第三方平台接入、云服务、游戏主机改造均不属于本计划。

工程细节只在[工程设计](localization-engineering-design.md)维护；本文件维护任务依赖、工作包、验收条件和证据要求。施工中若结构调整，同步改工程设计与受影响测试，不在本文件另起一份字段定义。

## 2. 施工组织与登记要求

实现根目录为 tools/localization/。施工前按 hierarchy 检查并登记实际使用／改动范围，创建文件后再加入实际目录。代码施工通常只需该独立目录及本计划相关文档；不得隐含占用或修改 engineering/、rulepacks/、游戏运行目录或根依赖环境。

依赖安装、构建、GUI 配置、生成样本和测试数据必须使用已登记范围：模块的 node_modules、dist、.test-output，以及测试显式指定的独立用户设置目录。不要在真实作者项目上运行破坏性、迁移或中断测试，不依赖当前游戏房间。

按工作包顺序推进。即使后续增加协作者，共享 schema、messages、storage 和跨模块契约也必须先冻结兼容基线再开展依赖工作；本计划不自动授权启动并行 Agent。每次交付释放自己的占用，不删除他人的登记。

阶段完成的共同条件：交付文件存在、必要测试通过、失败场景有证据、版本与环境可追溯、文档与真实能力对齐。GUI 截图只能证明布局或状态，不能替代文件与行为断言。测试失败、未执行或缺证据不能标记阶段完成。

## 4. 各阶段施工与退出条件

### L10N-0：独立工程骨架与技术试验

**前置**：核对需求边界与登记范围；无代码前置。

施工：

1. 建立 tools/localization 的独立依赖锁、workspace、contracts/messages/core/CLI/desktop/runtime 边界；只先创建真实需要的文件。
2. 固定 Node、Electron、TypeScript、React、构建器、Ajv 和 ICU 依赖，记录运行时与许可证；验证 Electron 内置 Node 和 CLI Node 的共有 API。
3. 创建可打开的独立空窗口、原生目录选择和 CLI 帮助入口；验证渲染器不能任意访问文件系统或执行 shell。
4. 用英文、中文、引号、花括号、复数和错误模板做共享解析试验；选择能驱动真实 Electron 窗口的测试方式。
5. 试打包最小 GUI 和 CLI，复制到仓库外隔离目录运行，提前发现发行路径和运行依赖问题。

**退出条件 E0**：

- E0-1：清空游戏相关环境变量后，GUI 窗口和 CLI 帮助均能启动，无 OnlineCOC 文件访问或服务请求。
- E0-2：目录选择支持中文与空格路径；选择项目不会执行目录内脚本。
- E0-3：同一 ICU 样本在 GUI 预览环境和解析库试验中一致；错误模板能被捕获而非直接返回原模板。
- E0-4：生产依赖检查没有模块外工程源码引用；保存精确版本、发行试验日志和 GUI 自动化决策。

证据：环境清单、依赖边界检查结果、空窗口截图、共享格式化样本结果、最小发行启动记录。若打包或共享格式化不成立，先调整技术栈与工程设计，不把风险留到最终阶段。

**2026-11-12 实施记录**：独立源码、锁文件、GUI/CLI/ESM/IIFE 最小构建及发行检查已经存在。2 组单元测试、类型检查、依赖边界、8 组打包真实窗口格式化样本通过；完整发行在仓库外普通用户权限启动通过。E0-2 已打开原生对话框并导航中文空格目录，Computer Use 子控件操作/截图失败，最终目录选择没有回传；用户暂时无法接管，未把该项记为通过。测试窗口已关闭，恢复方法与证据见[验收记录](../../tools/localization/docs/acceptance.md)。按阶段前置条件暂不启动 L10N-1。

### L10N-1：数据格式、读取与语义校验

**前置**：E0 全部通过。

施工：实现工程设计第 4 节的项目配置、目录、语言文件、翻译元数据、别名、术语、TextRef 与交换 schema；编写重复 JSON key 检查、路径规则、跨文件校验、C1 摘要及 effectiveStatus。创建两个通用样本和可复现的大数据生成器，不复制真实游戏包。

**退出条件 E1**：

- E1-1：新项目默认 en→zh-CN，语言文件可用外部编辑器直接读取，输出格式稳定；读取或查询不改写任何源文件。
- E1-2：原文、参数或语义说明变化使译文 needs-review；仅缩进、标签或样例变化不会误使原文摘要变化；外部修改 reviewed 译文同样失效。
- E1-3：缺目标值、空值、元数据缺失、源文缺失分别给出约定状态；格式错误、重复 key、别名环、回退环和参数类型错误给出可定位诊断。
- E1-4：不支持 schema 版本以只读打开；extensions 往返保留；未知业务字段不自动执行。
- E1-5：同名 key 在不同 projectId 隔离；大小写路径碰撞、Windows 保留名、`../`、目录连接逃逸被拒绝。

证据：schema 正反样本矩阵、摘要测试向量、状态推导结果、路径边界报告。这里的“校验通过”不表示翻译完整，缺译仍为可降级状态。

### L10N-2：可恢复文件事务与 CLI

**前置**：E1 全部通过，数据契约可用于计划与结果验证。

施工：实现 Workspace Snapshot、ChangePlan、项目写锁、before/after 事务、COMMIT/DONE 恢复、反向计划撤销及基础 CLI。建立故障注入点，覆盖 COMMIT 前后与每个替换步骤。实现 query/plan/apply/validate/recover，后续命令未实现时明确报不支持。

**退出条件 E2**：

- E2-1：预演列出全部受影响文件与词条，未 apply 时磁盘不变；apply 以相同基线提交，过期计划返回冲突而非覆盖。
- E2-2：两个进程保存同一项目时实际写入串行；同一条目不同修改不能最后写入者静默获胜；不同项目互不阻塞。
- E2-3：在无 COMMIT、有 COMMIT、部分文件替换和 DONE 后逐点强制退出，重启得到工程设计规定的恢复结果，不把半批文件作为正常快照构建。
- E2-4：恢复期间文件被外部改为第三个值时停止，保留 before/after/current；不以“修复”为由覆盖新内容。
- E2-5：锁归属不能确认时拒绝写入；磁盘满、只读目录或 Windows 文件占用不会显示成功，也不损坏原始文本。
- E2-6：CLI 的 JSON 输出与退出码符合契约；撤销已保存操作同样进行摘要检查。测试只操作隔离样本。

证据：逐故障点的进程日志、事务状态、恢复前后文件摘要、并发保存报告、CLI 契约结果。未通过 E2 时，GUI 只能只读浏览或暂存编辑，不能接入正式保存。

### L10N-3：可视化增删查改与作者工作台

**前置**：E2 全部通过；GUI 复用已验证应用操作，不另写文件层。

施工：实现工程设计第 6 节的项目向导、工作台、过滤、详情、ICU 分支表单、源/译文编辑、审校、语言设置、变更预览、撤销、外部变动提示与恢复入口。引用扫描尚不完整时明确显示未知，不伪造使用次数。永久删除和重命名的完整接入放在 L10N-4。

**退出条件 E3**：

- E3-1：人从空目录在 GUI 完成新建项目、增加英文词条、填写中文、预览和保存，关闭后重开一致，无需手改 JSON。
- E3-2：搜索原文、译文、key、语境并组合状态/语言过滤；点击结果正确打开该条目。大表格不是一次渲染全部行。
- E3-3：修改英文原文提示中文待复核；修改中文不会覆盖英文；审校状态、缺译与语法错误的显示准确。
- E3-4：可删除某语言译文并预览回退；可停用词条；有未完成扫描时永久清理被明确拦截。新增/禁用语言同步检查回退链。
- E3-5：批量操作展示数量和实际文件差异；保存中断后能进入 E2 的恢复流程。外部修改遇到脏编辑时不覆盖当前草稿。
- E3-6：Tab、键盘定位、Ctrl+S、撤销/重做、关闭未保存提示可用；长文本、150% 缩放及 1280×720 窗口不遮挡保存与取消操作。

证据：真实窗口操作记录、关键截图（新建、表格、详情、缺译、错误、外部修改）、每个动作前后磁盘断言。不能只验收“按钮存在”。

### L10N-4：引用管理、导入导出与文件协作

**前置**：E3 全部通过；复用 E2 的批量提交和冲突模型。

施工：实现 JSON TextRef 扫描/改写，JS/Lua 字面量扫描及覆盖说明；实现动态引用保留、key 重命名和别名、停用后清理。接入 JSON/CSV 交换与 base/ours/theirs 三方合并，GUI 和 CLI 共用同一导入预演。

**退出条件 E4**：

- E4-1：JSON 引用重命名一次事务同步词条、译文、元数据和引用；旧消费者需要时生成同语义兼容别名。
- E4-2：JS/Lua 动态拼接、未支持文件和未知扫描范围显示为不完整；不自动改写不支持的位置，不自动删除其可能引用的 key。
- E4-3：删除仍被引用的词条要求先替换；重命名冲突、别名成环和目标失效被阻止；旧发布资源不受删除影响。
- E4-4：中文、引号、换行、逗号、以公式符号或单引号开头的值完成 JSON/CSV 往返；必要转义可还原，不误改原文。
- E4-5：导入旧源摘要不自动变成 reviewed，缺行不当作删除；同一 key 的冲突要逐项解决，不同 key 可合并。
- E4-6：模拟 Agent 直接编辑文件，GUI 可识别并合并；GUI 保存产生同规范最小差异。外部平台扩展元数据往返保留，无需真实接入平台。

证据：扫描覆盖报告、引用前后对照、重命名中断恢复、交换文件及往返摘要、三方合并样本、GUI 差异截图。

### L10N-5：资源构建、解析库与独立消费

**前置**：E4 全部通过。构建使用稳定文件快照，不能直接遍历可能变化的源目录作为同一版。

施工：实现正式构建、public/restricted 分类、别名规则、清单与资源摘要、完成标记及版本验证；产出 ESM/IIFE 解析库和无游戏后端的浏览器演示。GUI 发布面板和 CLI build/verify 接入同一构建服务。

**退出条件 E5**：

- E5-1：中文全部缺译仍能构建，退出码为 0 且报告完整；默认显示英文，源文也缺时走 ref.fallback/errorText，全部兜底缺失时返回内置提示。
- E5-2：errorText 模式在目标缺失后直接显示指定字段。未知 key、坏参数、格式化失败、缺文件和资源加载失败都不会从 resolve 抛出文案异常。
- E5-3：同一输入产物摘要可重现；只改构建时间不改变资源修订。变更译文形成新版本，旧目录逐字节不变。
- E5-4：public 输出、清单、contracts、aliases 和报告分发边界均不含 restricted 条目；公开别名不能把受限目标导出。未知词条不自动公开。
- E5-5：构建中途源文件变化时采用已固定快照或拒绝，不混合两版；中断构建不产生可误认为完成的目录，不覆盖旧资源。
- E5-6：两个静态页面用不同语言显示同组固定参数；两个项目同名 key 不混用；dispose 后旧加载结果不进入新实例。关闭 GUI、断网仍可使用已交付资源。
- E5-7：显式请求旧 resourceRevision 时只使用该版本；不存在则返回约定错误文字，不静默改用最新；manifest 文件缺失、摘要损坏可诊断。

证据：构建可复现报告、公开／受限泄露检查、解析行为矩阵、浏览器实测、旧版本对照、关闭编辑器和离线消费记录。通过本阶段不代表实现了游戏玩家授权或存档集成。

### L10N-6：发行、性能与完整交付

**前置**：E0～E5 全部通过，已有功能候选版本。

施工：独立打包 GUI、CLI 与解析库，生成 release.json、摘要、依赖/许可和实际使用文档。将发行物复制到仓库之外的新环境，清理与原工程关联，执行完整任务、性能、路径和读写权限验证；整理当前工程说明与发布证据。

**退出条件 E6**：

- E6-1：无 OnlineCOC、无具体配置包、无系统 Node/npm/Python 的 Windows 11 x64 环境中，GUI 和 CLI 可离线运行；不请求管理员权限或临时下载安装运行时。
- E6-2：检查实际进程、文件访问和生产依赖：不访问 engineering、rulepacks、游戏用户配置或房间端口。工具自身用户设置目录允许存在并有记录。
- E6-3：完整任务由人类测试者仅使用 GUI 完成；再由 CLI/直接文件编辑修改同一项目并由 GUI 接收，双方使用同一契约。
- E6-4：达到工程设计第 10 节容量与性能目标；每项报告记录机器、数据规模、重复次数和 P95，不以一次主观感觉代替。未达标则优化或明确修订目标后重验。
- E6-5：中文/空格路径、便携目录移动、只读安装目录和独立设置目录均可用；复制项目与所需资源后可恢复，不依赖原绝对路径。
- E6-6：所有发行文件通过摘要检查；完整发行目录、CLI 的独立 Node 与解析库使用方式均有说明。未知系统、网络盘和物理断电不被列为已验证能力。
- E6-7：无未解决的文件丢失、静默覆盖、受限泄露、缺译崩溃、依赖耦合或必需 CRUD 不可用问题；实际文档、文件索引和登记已同步。

证据：独立环境说明与运行日志、完整人类任务记录、性能报告、发行摘要、依赖/文件访问审计、已知限制清单。缺少独立环境时不能将 E6 标为通过，应如实记录尚未执行。

| fallback/errorText 不打断调用方 | E0-3 | E5-1、E5-2、E5-7 |
| public/restricted 导出隔离 | E1-5 的路径校验 | E5-4 |
| 资源版本可复现、历史不覆盖 | E2-1 | E5-3、E5-7 |
| 平台接入的数据准备 | E1-4 | E4-4～6 |
| 性能和独立发行 | E0-4 的初试 | E6-1～6 |

## 6. 人类开发者最终验收脚本

使用全新临时目录，不安装或启动 OnlineCOC：

1. 打开 GUI，新建项目，确认默认 en→zh-CN；添加按钮文案和带 count 参数的槽位消息。
2. 填中文并审校；搜索定位，编辑英文，观察中文变为需复核且原译文保留。
3. 修改中文、预览不同 count；故意写坏模板，看见可定位错误并保存草稿，随后排除该译文。
4. 从文件系统直接改另一个词条；返回 GUI 接收变更。再制造同一 key 双方修改，逐项解决冲突。
5. 创建 JSON TextRef，重命名 key，检查引用差异；尝试删除仍使用的词条，看到阻止和替换入口。
6. 删除某个中文译文，发布不完整版本，观察英文 fallback；切到 errorText 模式并再次验证显示。
7. 标记一个词条 restricted，构建后检查 public 清单与文件均不包含它。
8. 导出交换文件、在外部编辑再导入，预演并应用；关闭和重开 GUI，检查保存结果与审校状态。
9. 关闭 GUI，用独立演示页面加载公开产物，切换语言；只复制发行和项目文件到新目录后再运行。

记录每步的预期、实际、文件差异和证据路径。自动化覆盖内部一致性，人类任务验证可理解性；两者都需完成，不互相替代。

## 7. 证据、报告与阶段收尾

每阶段在已登记的 tests/output 或 .test-output 范围保存机器报告，格式至少包括 stage、sourceRevision、toolVersion、dependencyLockHash、OS/CPU/RAM、fixtureHash、开始/结束时间、cases（id、expected、actual、passed、evidence）以及 unresolved。截图不得含真实私密文案或其他用户目录内容。

阶段状态更新为进行中/完成时必须附实际证据与未验收范围。本施工文件作为计划整体在未完成时保留计划状态；阶段全部通过后，将真实用法、文件格式和验收总结整理到工具自己的 docs 与工程索引，再按维护标准归档计划。原需求边界持续有效时可保留入口，避免重复维护两份协议正文。

文档纯修改只检查格式、链接、示例与互相一致；代码施工按受影响模块运行必要测试。每阶段通过后无需无理由反复全量测试，新增失败、契约变化、打包或风险变化才扩大检查。最终发行必须执行 E6 的完整边界验证。

## 8. 待验证的工程选择

精确版本、Electron 自动化驱动、Windows 文件替换行为、发行体积与性能目标需要在对应阶段实测。这些不改变已确认的产品约束。若发现必须依赖游戏主机或特定包才能完成某阶段，应视为设计偏离并修正依赖，不能直接扩大到核心工程施工。

首版之外的协作平台、其他操作系统、网络共享目录、自动更新与代码签名需另行规划；当前不为它们创建服务、账号或部署任务。
