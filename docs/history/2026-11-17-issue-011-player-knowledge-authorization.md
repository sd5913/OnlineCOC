## 结论与职责

2026-11-17完成记录：通用宿主知识服务、Room v4、显式转换、SDK、联网出口、AI严格消费及两个示例已通过验收。详见[现行服务](../current/engineering/player-knowledge.md)与[验收记录](../../engineering/acceptance/knowledge/README.md)。未修改正式存档或部署云端。以下评估保留原决策背景，不作为现行接口说明。

建议在引擎通用业务层增加可选的“个人知识记录／资料披露与授权投影”能力，独立于 AI 启停工作。配置包仍决定何种行动构成发现、允许知道哪些内容；AI 只消费宿主授权结果。以下均为提案，不表示已新增引擎接口。

| 放置方案 | 收益与问题 | 评估 |
| --- | --- | --- |
| 全放配置包 | 玩法自由；每包重复实现身份、版本、撤回和查询，普通宿主接口可能不使用同一规则 | 继续承担业务规则，基础记录与授权适合共用 |
| 全放 AI 模块 | 便于约束模型资料；不能覆盖地图、普通 API、资源分发，关闭 AI 后不应丢失知识 | 不适合作为权威存储与访问控制层 |
| 引擎可选能力＋包规则＋AI 消费 | 统一权限、回执与来源；需要处理投影契约和存档版本 | 推荐，按显式能力注册分期接入 |

引擎不硬编码 Stumpsville 的地点编号、NPC 发现条件、`locationKnowledge` 字典或“进入即获得全部线索”。文件存储模块只负责持久化；知识领域逻辑放在引擎业务层，不进入通用文件读写库。

## 建议的最小能力

### 1. 区分经历、授权和事实

“经历过／收到过消息”是有来源的记录，“当前允许读取”是权限决定，“消息内容是真的”是游戏事实判断。聊天传闻可成为个人证据，不因此成为权威事实；模型推断不能自动写入已知记录或授予读取权限。

建议使用版本化知识／披露记录及其有效投影。候选字段如下，最终类型名、命令和集合位置由工程评审冻结：

| 字段组 | 要表达的内容 |
| --- | --- |
| 身份与作用域 | 房间、包命名空间、记录 ID、revision；主体为账号或角色引用，角色与账号控制关系由宿主验证 |
| 可读对象 | 稳定资源引用及包注册的内容分面，例如基础名称、公开描述、单条线索；不接受客户端任意 JSON 路径 |
| 内容版本 | `observed_revision` 固定所见版本；`live_scope` 明确允许读取指定分面的后续发布版本 |
| 依据 | 进入／行动结果／KP 揭示／经确认的分享等来源类型，来源引用与版本、执行回执或决定引用 |
| 生命周期 | 有效、被替代或撤回；宿主记录操作人、时间、幂等键和变更审计；有效授权修订可用于失效检查 |

场景观察和定向揭示默认固定版本，首版纳入小型授权分面不可变快照。live_scope 只用于明确持续告知的本人状态／指定公共规则，首版不做场景位置订阅。固定快照完整且当前仍有保留授权时，原实体更新或删除不单独使旧观察失效；快照缺失或不可复验时拒绝读取，不能用最新内容冒充旧观察。正文、名称和引用详情必须使用同一版本，具体例子与失效矩阵见[PL 细则第 3—4 节](../current/design/ai-player-knowledge.md#3-固定观察与持续披露)。旧档不自动改变。

主体默认保持账号级以兼容当前包；契约预留角色级，启用后单一会话绑定一个明确的知识主体，不能因账号拥有多个角色就自动合并知识。转让角色、退出房间及恢复存档时需重新检查控制关系。

### 2. 统一授权投影与注册边界

引擎提供读取投影、记录查询、披露／撤回的受权操作以及可复验的授权修订。配置包注册资源类型、可披露分面、投影器和可信业务入口。登记经历不等于获得任意字段的访问权；一次有效记录只授予所声明的分面。

启用方式必须显式：既有未接入资源继续遵循原 public／owner／kp 语义；接入资源声明个人披露策略并在所有相关出口生效，不把全工程 public 静默改义。发布内容与选择受众成为两个独立决定。严格策略须由宿主持久记录，独立于适配器进程与 AI 启停；缺失、失败、版本不支持或恢复未核验时拒绝相关读取，不回退到原始实体。未接入包的普通游戏入口保留兼容语义，但不能据此开放严格 PL AI 游戏资料；后者要求知识能力核验。故障与恢复规则见[PL 细则第 5 节](../current/design/ai-player-knowledge.md#5-严格模式的持久声明与故障规则)。

KP 可以通过注册的披露操作向指定玩家开放秘密对象的允许分面，例如 NPC 的名称；这不等于开放其完整实体、模板或其他私聊。资料本身的参与者、密级及外发约束不能被一条知识记录任意覆盖。公开聊天中的事实若需要转为个人线索，必须经包规则或 KP 确认并生成独立的授权摘录。

应核查并接入普通快照／查询、AI 查询与引用、实时订阅／重连补发、关系端点、行动目录／回执、玩家导出和资源访问。地图、图片、名称、本地化文本、搜索提示、计数与错误反馈都可能携带内容，不能只删除实体 description。服务端执行仍使用权威完整状态；读不到资料不应使合法规则错误执行。

### 3. 写入、撤回与一致性

记录写入复用宿主身份、命令封套、前置修订和幂等回执。KP 或宿主认可的包规则可记录经历／披露；客户端和 AI 不得自报“已进入”获取权限。引擎内的移动与发现可在同一事务提交；包侧独立存储通过可信提交回执确认后接入，未确认或中断时保持不可读，不制造已成功的知识记录。

撤回只停止后续数据读取及相关历史复用，不能抹去已展示给人的记忆。多条有效授权可能覆盖同一分面，撤回一条不能错误清除其他合法来源。内容修订与授权修订分别处理：原资料更新不会废弃仍有效的固定观察；持续披露只更新获准分面，内容变化使相关 live 查询和缓存重新核验。最后有效授权撤回、主体控制变化或快照不可用时停止相关读取。存在覆盖同一版本／分面的替代授权可重新签发证据，不机械清空全部知识；不得以不同版本替换旧引用或复用另一主体缓存。资料快照与授权修订在同一读取边界取得或在交付前复验。只读证据检查与修改执行基线分开，无关世界变化不打断只读回答，写入仍检查原基线。

知识命令如交给 AI 提议，仍走已有 KP 整批裁决；本 ISSUE 不新增模型直接写入权限。与 ISSUE-008 共享正式决定／回执引用，与 ISSUE-010 共用包事务约束；不重复实现裁决队列或跨存储提交协议。

### 核查结果与限度

调用当前 Host.project、entity_projection 和 Stumpsville Adapter.entities，使用合成房间对象及内存包数据，得到以下结果：

| 场景 | 本次核查结果 |
| --- | --- |
| 地点已发布，玩家未进入且未被揭示 | 普通视图返回 public 地点实体；AI 投影排除该地点 |
| 只向 player1 揭示 | AI 投影允许 player1 读取，player2 仍被排除 |
| 揭示后修改 published 正文 | player1 读到新正文，证明当前是持续读取语义，而非固定观察版本 |
| 移除适配器 | AI 实体投影恢复默认 visible 过滤；尚无独立的“必须启用个人披露策略”声明 |

核查未初始化 Host、未写存档、未启动 HTTP／WebSocket 或调用模型，不等于完整集成验收。另静态确认 [server.py](../../engineering/backend/src/onlinecoc/server.py)的 `/view` 与 WebSocket 快照共用 Host.project；[assets.py](../../engineering/backend/src/onlinecoc/assets.py)按 public／KP 控制素材读取；Host.receipt 仍复用原 visible 判定。现有5组包侧验收验证了个人 AI／包页面边界，没有证明所有这些入口已经统一。

这不是对既有 public 语义的自动否定：当前工程明确允许公开基础实体。缺口在于包声明“只向已探索者披露”时，各出口不能共同执行该策略。首版必须显式启用，不静默改变所有旧包的 public 含义。

### 建议先冻结的决定

1. **首版按账号授权，角色级先保留扩展位置。** 多角色独立知识需要同时改会话身份、角色转让与历史复验，不应作为堵住当前投影差异的前置工程。未支持的主体类型明确拒绝，不能偷偷合并到账号。
2. **统一服务放在宿主业务层，读取与执行权限分开。** 已有 AI adapter 可以作为迁移桥梁；普通视图、查询和实时快照不应反向依赖 AI 服务启停。获得 NPC 名称分面不等于获得完整实体、模板或操作权限；资料投影也不能把权威执行状态裁剪后交给规则执行器。
3. **版本模式必须显式。** 早期复评曾建议沿用 Stumpsville 的 live_scope 先行；用户随后明确要求 PL 辅助完全基于已知内容，因此该建议被本次协商替代：首版纳入小型分面固定快照，场景重新进入／可信观察／KP 揭示才生成新记录，live_scope 限于明确持续告知的本人状态／公共规则。缺少固定版本时严格场景资料不可用，不以最新内容替代。
4. **先列出口矩阵，再安排分期。** 最少列出普通视图／集合查询／实时快照、AI 查询／引用、关系／动作回执、素材／玩家导出；每种已注册资源标明是否涉及该出口、如何过滤、是否允许公共导航占位。未能实施过滤的相关出口须关闭或拒绝严格资源读取，不能以“后续接入”继续暴露原始内容。仅在对应出口完成验收后宣称该资源支持严格披露。
5. **将知识授权修订纳入令牌及缓存绑定。** 当前 Host.views 的键仅有账号、成员 authorizationEpoch、实体 ID 和实体 revision。知识撤回可能不改变后两类修订，不能只删 UI 条目；新策略需绑定主体、分面／版本模式及有效授权修订，在引用、缓存、重连和最终返回边界复验。具体复用或新增修订字段在 K0 冻结。

### 分期及依赖建议

复评建议先做契约与出口矩阵，再形成账号、小型分面固定快照、持久严格策略、KP披露／撤回及普通视图与AI同步读取的最小闭环，最后接包侧进入／发现和第二个最小包。正式K0—K5编号及具体依赖现以施工计划为准。角色级、场景自动持续观察和大规模历史管理延后；固定小快照是严格PL场景接入前置条件，不能延后却宣称已完成。

原生宿主披露命令不必等待 ISSUE-008 完整请求决定模型、ISSUE-010 配置删除或所有跨存储事务完成。依据可先绑定现有可信命令回执，后续决定引用按明确版本扩展；只有需要写入包独立存储的发现动作才依赖包侧提交／对账契约。权威记录可以继续使用当前文件数据管理模块；是否新增 Room 字段及其版本升级须在 K0 确认，无需为此先引入数据库。
