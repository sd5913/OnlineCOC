## 1. 首版交付定义

首版须交付一个可关闭 AI 运行的个人披露服务：账号主体、持久严格策略、小型固定观察、受限持续告知、KP披露／撤回及幂等回执、统一读取、SDK和最小管理入口。Stumpsville 以及第二个非地点最小包通过同一契约。Room v4、备份恢复及显式离线转换同时交付。

严格PL辅助需要的证据输出与引用细则由AI消费侧实施：只展示可复验的授权片段／结构化事实和可信模板；不能用一次真实模型未剧透代替权限验收。自由叙事生成、多角色、跨库原子事务、配置删除、向量检索和大媒体历史不进入本轮。

阶段间可使用桩和测试包开发，但涉及的所有读取出口完成前，不向真实玩家启用受控资源的严格模式。不会为了先显示新面板而暂时保留未过滤出口。

## 2. 施工分工与顺序

以下均为拟修改范围，实际施工前按 hierarchy 重新登记；此表不创建路径，也不占用未来工程范围。

| 阶段 | 主要改动范围 | 交付与退出条件 |
| --- | --- | --- |
| K0 契约冻结 | `engineering/contracts/`、引擎／AI设计文档、测试fixtures | Room v4、Knowledge模型、命令／查询Schema、DTO、稳定错误码、受控选择器、出口矩阵、来源版本／授权失效矩阵及示例；机器契约正反例通过，各消费者共同对齐 |
| K1 权威记录 | `engineering/backend/src/onlinecoc/knowledge/`、model/host/room_lifecycle、backend tests | 策略绑定、观察／持续授权／撤回、容量约束、主体绑定、幂等及同宿主事务钩子；AI关闭通过；故障注入证明不会半提交或重复记账 |
| K2 统一读取 | host/server/gateway/assets、数据查询、SDK、相关联机模块 | 统一投影与ReadProof，HTTP／WS／InProcess一致；关系、目录、规则结果／回执及素材／导出处理齐全；严格提供方故障阻断；全部旁路负例通过 |
| K3 AI消费 | `engineering/ai/`、backend ai_sources/publication、引用组件及共享契约 | 分开只读证据复验和执行基线；knowledge种类、快照引用详情、发送前／后复验及严格PL展示；既有发布校验不弱化 |
| K4 包与管理接入 | `rulepacks/stumpsville/`、第二最小包、SDK及管理面板 | 地点／NPC身份等有限分面、KP披露／撤回、明确版本标签；宿主移动事件自动观察试点；包独立发现无可靠回执时保持KP操作，不伪造自动支持 |
| K5 版本与发行 | backend转换／校验入口、测试存档、启动／导出脚本、当前文档／索引 | 显式v3→v4独立输出转换、旧知识“现在揭示”预览／确认、冷启动恢复、各支持联机路径、全量相关回归与交付报告；迁移前后数据与原备份可核对 |

依赖为 K0→K1→K2；K3 可先用 K0 的确定性桩开发，完成验收依赖 K2。K4 的 UI 可先用桩，正式接线依赖 K1/K2，AI部分依赖K3。K5转换方案与fixtures从K0开始准备，最终发行在K1—K4全部通过之后。

不以工期天数替代退出条件。预计改动集中在 K2 各出口和 K3 证据校验；UI复用现有SDK与管理布局。若发现未列出口，先补矩阵和占用，再施工，不能只补提示词。

## 3. K0 必须产出的契约材料

- [x] 按[设计](2026-11-17-player-knowledge-engineering-design.md)第4—7节形成机器Schema：PolicyBinding、Subject、ResourceKey、Observation、Grant、KnowledgeRef、KnowledgeItem、KnowledgePage、ReadProof，以及4项宿主命令和5项读取／预览接口。
- [x] 所有字段标记required、unknown-field策略、类型、长度／大小上限、revision、哈希canonical方法；稳定排序和分页cursor给出正常／过期样例。
- [x] 固定观察和live分开测试：原正文更新、单条grant撤回、等价授权存续、成员重建、提供方缺失、恢复分叉。
- [x] 注册描述符及代码装配路径固定为本机受信入口；缺失adapter时仍能从存档策略识别受控实体和资产。严禁模型指定提供方代码或路径。
- [x] 普通入口／KP管理／玩家AI会话的AudienceContext明确分开；不得因实际调用者为KP而扩大玩家会话权限。
- [x] 明确旧Entity与KnowledgeItem的差异，SDK不把部分资料转换成可写实体；对旧客户端的行为是服务端过滤或明确拒绝。
- [x] 生成“出口→涉及资源→过滤或拒绝→测试编号”清单，不允许空白；新增HTTP路由同步P2P/web受限白名单，不使用放宽任意代理作为接入方式。

K0可以修正字段名以符合仓库命名规范，但必须一次同步工程设计、机器契约、AI消费者及样例，不保留多套对同一概念互相矛盾的协议。

## 4. 验收矩阵

下列编号是验收义务，不代表测试函数数量；实现可拆分更多用例。全部使用独立合成数据目录与确定性模型桩，真实存档不参与。

| 编号 | 场景 | 必须满足的结果／证据 |
| --- | --- | --- |
| K-01 | 无策略的旧玩法／新v4空knowledge | 保持legacy行为；能力不谎报严格模式，未改变全局public语义 |
| K-02 | 地点已发布、PL未进入／未被揭示 | `/view`、集合查询、WS、AI搜索／引用中均无受控名称与正文；仅显式公共导航分面可见 |
| K-03 | 只向一个成员披露 | 另一成员复制resourceId、grantId、完整ref、cursor和URL均不能读；无隐藏名称／计数错误泄漏 |
| K-04 | 观察之后修改原正文 | 老引用、历史详情、普通资料页仍显示原观察；新观察另有ID／序号；不替换旧快照 |
| K-05 | live内容变更而授权未变 | 新读取见授权新内容，旧缓存／引用重新校验；一次到访不能订阅场景未来秘密；持续资格丧失立即拒绝 |
| K-06 | 两条grant对应同一观察；逐一撤回 | 撤第一条仍可读，撤最后一条不可读；不同观察的授权不能相互替代 |
| K-07 | PL伪造到访／provenance／observedAt | 公开管理命令拒绝；错误不写观察、不增加授权，不修改游戏状态 |
| K-08 | 同commandId重试、异参数碰撞、过期revision | 原参数返回原回执；碰撞拒绝；并发KP不覆盖；一次来源事件只记一次 |
| K-09 | 写入前／提交后响应前崩溃和重启 | 观察＋grant＋回执要么一起提交要么均无；原宿主动作与自动观察同事务；未知结果先查回执 |
| K-10 | 缺失／异常／不兼容／启动未就绪提供方 | 存档严格声明仍在；普通读取和AI均阻断，旧缓存也不能作可读依据；恢复后重新验证 |
| K-11 | 实体进入受控选择器、策略改版 | 新对象立即受控；旧DTO、令牌和cursor不可绕过。策略冲突拒绝绑定，不按加载顺序放宽 |
| K-12 | 登录失效、退出、成员删除重建、多账号同名 | 拒绝旧主体授权和会话；不能因account显示名相同继承旧grant |
| K-13 | KP管理员与玩家级会话 | KP管理可查看合法管理资料；查看／执行PL会话严格使用绑定玩家；私聊参与者限制继续生效 |
| K-14 | 不相关角色移动／他人授权变化 | 实际只读依赖不变时回答和历史仍有效；修改批次／配置发布仍因其原基线变化按规则拒绝 |
| K-15 | 知识撤回时实体revision没变 |旧viewToken、引用、缓存及操作资格不能依靠旧revision继续读取或执行；无expectedViews也不能绕过操作权限 |
| K-16 | 查询／工具追加／模型发送／完成／历史复用各边界撤权 | 未发送内容不外发；已发但回收前撤权的答案不作为有效答案展示；无法收回已发请求的限制如实记录 |
| K-17 | WS分块中撤权、断线重连、切换用户 | 分别在最终发送资格检查前后设置屏障：撤回先发生则不排队旧end，已排队内容按已外发边界处理；reset后清除临时块；新登录不沿用前用户snapshot、缓存或详情 |
| K-18 | 关系、进度、wait选项、规则目录／计算结果／旧回执 | 无注册安全输出时拒绝或移除受控正文；状态回执不夹带秘密；合法权威计算仍使用完整主机数据 |
| K-19 | 素材URL、附件、静态包、l10n、补全、导出 | 不仅检查页面DOM，还检查原始响应／分发文件；受控二进制未支持时直接拒绝，不暴露旧公共地址 |
| K-20 | 原始对象归档、来源硬约束撤回 | 固定历史与live分别执行设计规则；快照不可用时不拿最新正文补写；撤回不能谎称抹掉人的记忆 |
| K-21 | 超大正文、过多分面、容量／查询输出上限 | 统一错误，无静默截断、半授权、无界扫描或自动丢历史 |
| K-22 | 正常重启、备份恢复、同roomId不同副本 | 正常重启知识保留；恢复新scope，旧ref／客户端失效；幂等回执不会驱动重复执行 |
| K-23 | v3转换及旧locationKnowledge导入 | 原备份字节不变；独立v4结果校验通过；无虚构旧时间／来源；KP确认后仅记“现在揭示” |
| K-24 | AI关闭、provider网络不可达 | 普通披露管理／查询／撤回／恢复正常，调用次数为0；权威存储不在AI仓库 |
| K-25 | 第二最小包 | 使用“物证描述／已公开规则”等非地点资源，无Stumpsville编号或字段硬编码 |
| K-26 | 严格PL回答与手选旧引用 | 返回片段确属当前授权的具体版本；标签也绑定同一快照。自由事实文本、伪造引用、跨主体引用不直接展示；历史聊天缺少受众／序号证据则不外发；不能以模型推断新增发现 |
| K-27 | 既有基线回归 | 主机管理、聊天室参与者权限、文件故障恢复、Lua/Flow、AI A/B/C和发布、PL/KP会话及联网分发的受影响测试全部通过 |

模型内容检查与权限检查分开记账：确定性桩记录全部实际外发payload；可以在必要时按已有用户授权做小规模真实模型体验测试，但它不是权限验收的必要条件，不因“没说出秘密”判定通过。

AI消费细节补充执行[设计细则 D01—D16](../current/design/ai-player-knowledge.md#9-验收与设计待定项)，作为K3/K4退出条件；它们与K-01—K-27有重叠，报告分别列覆盖关系而不累加数量。

## 5. 性能与资源验收

K0保留当前同机基线，K2/K3使用相同机器、相同生成数据对比；报告机器配置、数据规模、冷／热状态与计数，不作无证据的延迟承诺。

- 小样例：2名PL、30个资源、100条授权；用于完整交互和HTTP/WS/AI接线。
- 中样例：20名PL、1,000个资源、5,000条授权、快照总量不超过8 MiB；每主体查询50项并读取12引用，重复至少100次。
- 容量边界：分别触发设计限制及单次输出限制；全部显式拒绝，无进程崩溃／未记录提交。
- 采集 search/read/recheck p50/p95、持久文件加载次数、provider pin/read次数、Room提交字节数、WS单次投影大小；所有后台测试输出进入独立测试目录。
- 结构性门槛：同一读取或复验不能按每条ref反复加载整份包文件；每请求每提供方最多捕获一个一致版本，复验允许一次必要重取。一个查询必须有有界分页；不得因两个用户共享缓存省去身份检查。
- 延迟门槛：同机中样例warm p95不高于K0等价legacy读取基线的2倍加20 ms；若旧基线不包含某类新接口，分别记录绝对值并在K0评审冻结目标，禁止临交付时自行放宽。文件全量提交成本超出交互需求时先报告并优化索引／快照，数据库仍为后续独立决策。

## 6. 包切换及上线步骤

1. 完成K0—K3合成包测试；此时不修改正式房间，不把未完成能力写入current文档。
2. 对独立 Stumpsville 副本导出完整备份，转换为v4，再验证加载、资料分面和玩家导出内容。保留原始v3备份及摘要。
3. KP预览旧知识导入选择；对明确选择的成员／资源执行“现在揭示”，不默认把全体published地点授予所有成员。
4. 绑定严格描述符后检查全部出口 ready/denied，才允许玩家连接；新旧包不能同时向两个知识账本写入。缺少源资料／提供方时保持blocked。
5. 停止旧服务，加载新宿主、包代码与SDK，网页重新导出通用静态资源；只刷新浏览器不足以替换后台。
6. 在副本上验证两玩家、KP、AI关闭／开启、LAN及已提供的P2P/web路径；最后才形成上线说明。正式升级按用户已授权范围进行，不能把文档任务当部署授权。
7. 回滚恢复旧程序＋原备份，明确升级后产生的记录不自动反向合并。恢复到新副本的scope必须改变，不能保持旧引用可用。
