## 现象与预期

当前宿主接受旧房间格式，并在加载或恢复时执行升级。用户于 2026-11-14 明确要求：移除对旧房间格式的兼容；通过更新说明及变更日志说明各版本的数据定义和变化，由配置包开发者或数据持有方处理迁移。

预期每个引擎发行版本明确声明其唯一支持的房间业务格式。旧版、未知新版和不符合当前 Schema 的房间应被明确拒绝，不在正常启动、恢复、导入或运行时隐式转换。已有旧数据由持有方决定何时迁移，并提交符合目标版本定义的数据。引擎负责格式定义、可定位的校验结果和发布说明。

本 ISSUE 提交需求和建议，不在本次文档任务中删除兼容代码、不迁移或删除任何存档。目标引擎发行版本及具体 Schema 版本号由工程方确认，不将当前实现写成已移除兼容。

## 原因与候选处理

现有首测采用自动升级以继续读取旧档。新的用户要求改为由引擎公布版本契约、外部负责迁移，应明确替代原运行时升级策略。

### 1. 引擎加载边界

- 各加载入口使用同一当前房间格式常量与完整 Schema 校验，只接受该发行版声明的格式。未知新版同样拒绝，不能尝试降级解释。
- 从活动运行路径移除 `RoomV1` 校验分支及 v1→v2 自动转换。旧 Schema 可留在历史文档、旧发行包或可追溯提交中供迁移方查阅，不再作为当前加载器的后备解析器。
- 新房间直接按当前格式初始化，包括当前要求的 AI 控制及聊天结构；不能先造旧数据，再依赖已删除的迁移函数完成初始化。
- 核查“缺 chat 则补齐”等历史缺字段修复。当前契约所需字段由新建入口提供；旧形态的修补交给外部迁移。确属当前契约允许的可选字段及其默认语义，应在定义中明确，不与旧格式兼容混用。
- 保留当前格式的正常备份恢复、素材/摘要校验和身份绑定。恢复新作用域、撤销未消费批准、关闭自动接收及 AI 历史隔离属于恢复语义，应从迁移逻辑中分离并继续验收，不能随整个模块删除而丢失。
- 不支持的版本在提交新房间数据代、自动补字段或执行恢复后的业务操作前拒绝；不改写旧业务数据。锁文件等正常打开行为不应被误报为成功迁移。

### 2. 版本定义与更新日志

工程方在每次涉及数据格式的发行中提供以下内容，具体目录及日志名称由工程方沿用现有文档布局确定：

| 必须公布 | 内容 |
| --- | --- |
| 支持矩阵 | 引擎发行版本或可追溯提交 → 支持的 Room.schemaVersion；标出首次不再支持旧格式的发行版本 |
| 版本定义 | 对应版本的机器可读 Schema，以及字段语义、必需性、默认值、枚举、跨对象引用和校验约束 |
| 格式差异 | 新增、删除、改名及语义变化；不能仅写“格式升级”或只列版本号 |
| 迁移责任 | 配置包开发者／数据持有方负责转换、备份和验证；引擎不会自动迁移，未转换房间如何识别和处理 |
| 验证方法 | 如何对目标格式做校验；给出最小有效示例及典型失败字段/错误码，不强制由引擎维护历史转换工具 |
| 其他版本维度 | 明确 Room、Entity、AI 契约、文件存储封套、备份格式和配置包版本相互独立；不能把所有值为 1 的结构视为旧 Room |

尤其当前房间业务格式为 2，文件存储封套仍可为 1；本 ISSUE 不要求无关格式一起升级，也不要求每个引擎代码发布都提升 Room 版本。对已有合法数据产生不兼容约束的变化，应评估提升房间格式号，不能同号静默收紧后只报笼统损坏。

建议沿用或细化 `SCHEMA_UNSUPPORTED`，返回可公开的实际版本、支持版本和格式说明入口；“不支持的版本”与“当前版本数据不合法”应可区分。错误和日志不得泄露房间正文、凭据或其他私密资料。

### 3. 迁移职责划分

引擎方交付目标定义、历史定义获取方式、变更差异及校验契约。配置包开发者可以据此提供包专用迁移工具；数据持有方也可自行转换，并决定继续使用旧引擎还是迁移到新格式。迁移工具不作为当前引擎必须内置或长期维护的兼容路径。

迁移不仅是改版本号；引用、房间作用域、批准、回执和包侧存档关系都须满足目标约束。若某次迁移涉及 AI 批准失效等语义，版本说明应明示。真实存档的批量转换、删除及覆盖不在本 ISSUE 的引擎实现范围内。

## 实施步骤与验收条件

1. 工程方确定首个生效发行版、支持矩阵、文档落点及错误响应；记录替代现有自动迁移策略的决定。
2. 按当前格式统一初始化和校验，拆分恢复分叉职责，移除旧格式活动加载及自动升级分支。
3. 同步更新当前操作说明、格式定义、发行日志和受影响的测试/夹具；旧说明移入历史并保留替代关系。
4. 在隔离目录验收下表，当前格式回归通过后才标记实现完成。

| 验收项目 | 通过条件 |
| --- | --- |
| 新建／重启 | 新房间直接满足当前 Schema；正常重启不依赖迁移 |
| 旧版与未知新版 | 打开、导入及恢复均拒绝，给出一致、可定位的版本错误；旧 payload 与数据代不被自动更新 |
| 当前版本损坏 | 缺必需字段、非法引用或不合法内容被校验拒绝，不作为旧档自动修补 |
| 当前备份恢复 | 身份、素材、工件、回执等原有约束继续成立；恢复分叉的 AI scope、批准撤销及自动开关行为保留 |
| 外部迁移输入 | 由外部按目标定义转换的隔离样例可通过正常校验；仅改 schemaVersion、其余不满足定义的样例被拒绝 |
| 说明可用 | 开发者能从目标发行说明找到支持格式、旧/新定义、字段差异、责任划分和验证方法，无需靠读迁移源码猜测 |

不在本次范围：改变网络协议兼容策略、改写独立文件存储模块、统一所有模块版本号、为用户执行真实数据迁移。

## 工程处理（2026-11-14）

接受方向并在后端 0.2.0 实施。旧 v2 原契约允许缺 chat，本次改为必需字段属于不兼容收紧，因此 Room 升至 v3，而不复用 v2。移除旧格式解析与自动补齐，完整房间与执行投影分开校验；`room_lifecycle.py` 仅保留初始化和恢复作用域分叉。当前备份的身份、素材、工件、批准及 AI 历史约束继续执行。

已增加只读 `validate-room` 命令、可定位且不回显正文的错误、版本支持矩阵、历史机器 Schema 与字段差异。外部迁移输入由当前校验器验收，不提供隐式转换。没有修改真实存档或配置包数据；旧 v1/v2 需由持有方转换后再启动。验证结果见[专项验收](../../engineering/acceptance/room-version-policy/results.json)。

验收结论：367 项完整回归＋1 项恢复生命周期补验，共 368 项通过、0 失败；版本策略专项含 23 项。ISSUE-007 关闭并归档，ISSUE-008 保留后续契约与接线计划。
