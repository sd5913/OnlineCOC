## 当前行为

依赖后端 **0.3.0 / Room v4**。所有包启动方式均通过 `--knowledge-provider tools/knowledge_provider.py --knowledge-data-path <本房间package.json>` 安装受信提供方，与是否启用 AI 无关。新房间安装配置包时，KP 命令绑定 `stumpsville-personal-v1` 策略，覆盖 `sv.*` 实体。

| 数据 | 披露方式 | 后续变化 |
| --- | --- | --- |
| 地点 | 角色批准入场、可信移动／再次进入、KP 地点页“向玩家揭示”、已执行场景行动的明确结果 | 保存当时场景分面，不读取未来世界内容 |
| 本人角色／建角骰盘 | 安装／批准时由 KP 明确 `knowledge.subscribe` 持续告知 `sheet` | 仅本人安全实体投影；完整实体结构供现有角色表操作，私密 metadata 等不输出 |
| 公共回合状态 | KP 安装／启用时明确订阅 `play` | 仅 phase、round、autoResolve 持续告知；不披露世界实体 |
| NPC／角色身份 | KP `actor.reveal` 指定本人并生成 `identity` 固定观察 | 名称和当时位置固定；取消发现会撤回对应身份授权 |
| 私密主持状态、世界实体、模板、规则源码 | 无 PL 默认披露 | `/view`、查询、引用和模型不能回退到旧 public／owner 读取 |

地点观察包含当时允许披露的名称、描述、已公开及本人的线索、个人行动菜单、出口导航及这些出口在观察时的门状态。特征使用安全菜单标题，不复制完整场景特征或主持机制。出口可显示“未探索地点”，不同时披露目标地点正文。全局“发布地点”只准备可披露的当前内容，不自动增加任何玩家知识。

同一地点使用最新有效观察；出口连线按无向边去重，只有较大编号节点披露的通路也能画出。相邻两端有不同时间的门观察时，地图使用较新的观察。没有门状态的旧观察保持未知（灰点线），不会补造历史或回退到当前私密门状态。再次进入或KP明确揭示后，才取得新的门观察。03→08连线绕过07角色卡并与08→09分开，避免交叉误判。

玩家普通地图与 AI 使用同一知识记录，场景页标注观察时间及“非实时场景”。AI 通过 `/knowledge/search`、`/knowledge/read` 等宿主门面取得证明，并在发送／展示时复验。严格回答由模型选择证据、服务端固定排版，不展示模型自由推理或凭模组常识补写的故事。引用标签点击后显示原观察详情；撤回后不切换到当前世界数据。

## KP 操作

- **地点管理 → 向玩家揭示**：选择已发布地点和玩家；“额外揭示的已知内容”默认全部不勾选。勾选会把列出的事实告知所选玩家，再保存新观察；不会执行行动、改变库存或机关。未勾选不撤回曾经告知的事实。
- **地点管理 → 行动说明 · KP**：查看完整机制、玩家措辞和所需发现。这是主持管理资料，不是某一玩家的知识预览。
- **房间 → 个人已知资料**：查看前 50 项有效授权、撤回授权。更多记录通过 `/knowledge/grants/query` 分页查询。存在其他等价有效授权时，撤回一项不保证内容立即不可读。
- **玩家对话 → 请 KP 说明**：玩家发送该选项后进入“裁决”页的统一裁决队列，不循环调用模型，也不自动授予信息。KP可打开原会话、前往资料揭示、转交原需求或取消；转交仍按原玩家知识权限处理。
- 普通 AI 修改仍走管理员会话和既有裁决队列；知识读取证明不能用于执行修改。

## 旧房间

当前运行进程不会自动加载新代码。先停止旧实例并按宿主[格式说明](../../../../docs/current/engineering/room-format.md)显式转换 Room v3，再启动新版包；此次施工没有转换或修改正式存档。

2026-11-19 的菜单安全投影为 v2。旧房间处理顺序：

1. 停止旧进程，使用当前包代码重启；网页房间重新构建分发资源并重新连接。仅刷新页面不会替换宿主提供方。
2. 新提供方与已存策略不匹配时，知识状态为 `blocked`；PL 不得到旧菜单、引用或旧 AI 证据回复。
3. KP 进入 **房间 → 启用个人知识服务 → 确认启用**，显式绑定当前提供方。本人角色和公共回合按持续告知继续提供；原策略下全部固定观察（包括人物身份）仍不可读，不自动补新观察。
4. KP 在地点／人物页选择接收者和允许告知的内容，显式重新揭示；或由玩家此后真实进入生成新观察。**处理旧地点记录 → 现在揭示所选内容** 也只创建勾选项的当前观察，不补造过去经历。
5. 旧菜单版本的未提交自动／人工预设请求不能继续执行，需要重新选取已知做法；主事务已经提交的请求仍查原回执完成后续发布，不重新投骰或发物。

旧记录保持原字节，不重写为新安全内容。已看到或已导出的旧内容无法收回；本次未自动转换或修改正式房间。提供方缺失／故障时保持拒绝，不降级。只换代码或提高 `sourceRevision` 不足以废止旧固定观察，须采用下述策略版本与 guard。

## 行动内容与个人发现

PL 菜单仅来自其最新有效地点观察。未发现的选项在知识 HTTP、页面、AI 查询与引用中均不存在；直接提交隐藏或虚构选项统一返回“此做法不在本人已知行动中”，不透露存在性。服务端先验证菜单，再检查实际角色、位置、开场、资源及规则条件。观察中的做法不保证现在可执行；菜单外想法可自由描述并向 KP 申请裁决。

| 地点 | 初次观察可见 | 额外做法的个人前提 |
| --- | --- | --- |
| 入口／主门 | 观察、检查、直接尝试 | 获知对应机关后才显示解除连接／绑绳固定；未知伤害和分支不进入提示 |
| 庭院 | 查看池底、观察梯子 | `pool-treasure` 后才列出钱袋／鼠像及打捞 |
| 洗劫屋 | 搜查器具 | `pots-observed` 后才列出领取 |
| 蛛网屋 | 查看蛛网、试探呼唤 | `web-captives` 或 `villager-reply` 后才列出救援 |
| 大厅 | 观察厅堂 | `hall-company` 后才显示交涉 |
| 工厂 | 检查器具、辨认出口 | `factory-tools` 才列工具；`factory-exits` 才列门，出口或工具线索可解锁升降机 |
| 蛇笼 | 观察铁门、聆听 | 守卫／路线线索后才列接近；`snake-rhythm` 后列持笛安抚 |
| 熟成洞 | 查看奶酪、留意洞内动静 | `cave-stock` 后列取用；发现人物后才列交谈，不提前写出人物名、睡眠状态或北方据点 |

本人收到的行动结果、KP 定向披露以及 KP 明确选择公开的线索可以满足条件；另一人的发现和 `poolKnown` 等共享标记不能替本人解锁，再次获得基础地点观察也不能绕过。撤回观察不会清除已经发生的个人发现；全部等价地点授权撤回后，现有菜单与旧引用不可用；未来重新进入仍可基于本人曾经发现的事实生成新观察。这是撤回授权，不是抹除经历。

## 本人所持物品

本人角色 `sheet` 的 `metadata.inventory` 补充实际持有物品的名称、公开说明、伤害／用量等白名单语义；不输出完整物品库、原实体 metadata 或其他玩家装备。由现有物品编号解析，不创建物品或配方。它沿用已有角色持续授权，正文变化更新来源版本；场景分面、固定观察和授权守卫不变。概括查询先列举本人目录再读取分面，名称搜索无匹配不能解释为没有权限。

道具组合、新规则和新配置属于[创作申请](ai-permissions.md)，与未知资料披露分开；玩家仍不能直接发布定义。

## 提供方与开发者边界

`knowledge_provider.py` 只定义分面、可信动作、授权结果投影及观察触发；权威记录、版本、撤回、恢复作用域由引擎持久化。`knowledge_client.py` 通过公开 API 发命令，不写宿主内部存档。包查询不创建观察，不维护第二份新地点账本。

提供方的 `sourceRevision` 描述权威输入版本，不能依赖接收者。KP preview 与 PL pin 可返回不同分面正文，但须对同一源版本一致；不要把易变的工作流日志或全包文件写入次数当成场景版本。

同类配置包应默认提供知识策略与受信提供方，明确固定观察和持续告知。不要直接把完整场景状态、所有源码、公共目录或包内聊天当作已知资料。不同玩法可参考 [证词最小示例](../../../../engineering/ai/examples/knowledge-investigation.py)，其基于 AI 测试包的实体身份／证词分面。

首版按账号绑定，不支持角色隔离、场景持续订阅和自动生成事实摘要；缺少受众／时序证明的聊天与裁决不进入严格 PL AI。原包共享回顾、当前联系人与动态场景状态不作为严格 PL 数据出口；地点行动菜单来自观察快照。KP 的完整管理数据与正常聊天操作保留。

### 作者声明与兼容

`scene-actions.json` 原 `label/hint/process` 保留 KP 完整机制；行动增加 `player: {label, hint, requiresAny}`，做法增加 `player: {label, process, requiresAny}`。`requiresAny: []` 表示基础可见，非空数组表示至少已知一个线索 ID；行动与做法条件须同时满足。缺少／错误声明默认不展示，不能回退主持文本。`playerKnowledge` 是 KP 可选披露的事实目录，字段为 `id/location/title/text`；仅列入目录不会自动给 PL。

`scene_knowledge.py` 仅投影 `id/location/label/hint/choices` 及做法的 `id/label/process`，不输出条件目录或主持原文。旧原版 artifact 只有整条行动剥除 `player` 后与审核基线完全相等，才借用安全措辞；自定义旧行动需作者显式适配。补记旧规则已叙述的事实还要求**实际执行修订**的 `scene.lua` 与原版相同；自定义规则应在 `public.clues` 显式返回已告知执行人的事实，不套用原版结论。

策略 ID 仍为 `stumpsville-personal-v1`、契约版本仍为 1；提供方 ID 为 `stumpsville-known-v2-<声明摘要>`，分面使用类型化 Schema，`sourceGuard` 校验投影版本和声明摘要。更新安全语义时必须调整版本／摘要，不单改展示代码。`sourceRevision` 包含权威定义、发现、门与导航输入，与接收者无关；KP preview 和目标 PL pin 不会因菜单不同而版本冲突。与工程bro 1号核对后，现有绑定、固定观察、guard 和来源复验 API 足够，本次未修改引擎。

同类包默认应同时提供玩家措辞、个人发现条件、主持机制、分面 Schema 和旧证据失效策略；不要把“已进入地点”等同“已知所有分支”。通用单位／枚举展示契约仍是[引擎 ISSUE-012](../../../../docs/plans/Issues/issue-012-authorized-data-presentation.md)评估项，本修复不依赖它。
