## 读取与执行

| 场景 | 当前处理 |
| --- | --- |
| KP 查询 | 管理员全房间读取默认允许；包括宿主资料与包内地图、私密记录等分片。模型外发仍按设置选择；本机凭据不属于游戏资料 |
| PL 查询 | 先列举本人已知目录并读取相关资料；关键词无匹配不等于无权限。缺少未披露资料时可主动申请披露 |
| PL 创作／组合 | “提交创作申请”可直接提交需求；KP 接收后在私有管理员会话生成方案，后续修改另行人工批准，自动审批不能绕过 |
| KP 转 AI 处理 | 各类裁决以来源卡引用原申请与对话；当前发言者为 KP，原申请人单独标识。转交不执行原裁决，生成修改仍须人工批准 |
| KP 处理资料申请 | 裁决详情 → 选择披露资料 → 预览 → 批准并披露；真实 `knowledge.observe` 回执成功才显示完成 |
| 普通执行 | 创建实例、发放已有物品、恢复角色等生成运行时指令包，遵守普通审批策略；不设动作数量上限 |
| 高危修改 | 核心规则、地图／入口、物品定义、配置删除提交概要与完整候选；A/B通过后，C的可采纳风险交KP评估。KP须显式确认当前整包指纹和本次评估，不能自动批准 |

独立 **AI 设置** 显示调用、服务配置、三类外发、频道自动接收、全房间读取、资料查询、运行时修改、配置修改、玩家对话、资料申请、玩家创作申请、两种普通自动审批。高危人工确认是固定约束。更改权限后旧上下文须重新核验。

高危详情提供“接受并执行／拒绝／转 AI 处理”三个按钮及一个可选备注框。点击接受表示人工确认当前方案，包侧据此提交全部风险ID的确认文本和当前整包指纹；原三项必填问答已移除，服务端高危检查仍生效。执行结果和定位见[调试说明](ai-debugging.md#快捷取证)。

重启后的旧高危候选可能在批准阶段返回 `STALE_AUTHORITY`。只有当前修订存在明确的批准失败回执、没有发布记录且仍有审核权限时，包侧才开放重新检查。新修订继续由服务端核对原来源、权限、当前检查和整包风险，并须再次人工接受；相同内容的指纹可以不变，旧修订的拒绝不能作为新修订的执行结果。恢复步骤与结果未知的边界见[问题排查](ai-debugging.md#问题排查)。

新房间首次设置默认启用全部AI使用能力及公共、本人已知、KP资料外发，KP全房间读取与查询开启；PL仍只读本人已知资料。自动批准与频道自动接收默认关闭，配置发布仍由KP决定。只有一个可用服务配置时自动选用；没有或存在多个配置时，面板提示选择服务，房间仍可正常运行。已有房间的密码、权限与后续显式关闭值均不被重启覆盖。资料外发关闭时会说明缺少的范围，不将它解释为房间没有资料。公共操作Schema不包含房间私密正文，不因KP资料外发关闭而一并阻止。快捷设置与调试见[来源引用与调试](ai-debugging.md)。

## 配置与存量兼容

`ai_gameplay.py` 定义高危范围、数据Schema、稳定编号、出口引用与存量验证。物品和地点只追加新编号；既有编号不删除或重排。C使用作者声明的固定角色与真实角色探针，背包校验仅证明相应结构兼容，不证明完整剧情或数值平衡。

仅在C阶段出现的`EXTENSION_FORBIDDEN`、`LIVE_SCENARIO_COVERAGE_MISSING`及存量覆盖不足会列为可采纳评估：详情显示依据版本、风险、位置、证据和覆盖限制，KP可“采纳评估并发布”、拒绝或转AI处理，仍只需一个可选备注。未覆盖的结果不改写成已验证通过；同名错误若来自A/B或真实执行失败，仍阻止发布。其他格式、依赖和权限错误不因人工采纳而消失。

KP在AI设置中调整C判断依据，包括已有指标阈值、补充场景与说明；补充场景不会删掉包作者原有场景。保存后旧评估过期，需重新检查再裁决，批准绑定候选和依据／报告摘要。模型不能自行修改这套依据或自批准。修改模板后仍须通过实际新实例、规则或行动结果确认生效，发布不等于目标已经完成。

批准的地图／物品资料从宿主活动工件同步到包侧。新地点默认 KP 可见，新通道默认关闭；公开及定向揭示继续使用既有操作。包侧草稿与批准版本冲突时显示“发布已提交，包侧待同步”，保留原草稿与幂等回执，不能把宿主成功发布说成未执行。

包内地图、手记和历史等独立资料可以作为KP方案的参考，不再仅因来源标记而拒绝候选。AI读取当前宿主目标并完成技术检查后，裁决详情显示参考资料评估；KP选择“采纳评估并发布／执行”时提交绑定完整上下文摘要的确认，可与高危整包及C评估同次接受，仍仅有一个可选备注。参考来源候选不会自动批准，缺失或不匹配的确认由服务端拒绝。严格PL会话不能借KP确认升级权限；实际来源、结构、版本或存储目标无效时仍须修复。新增地图地点不等于创建网络房间、启动服务或任意修改本机文件。

## 常用游戏用语

`ai/game-terms.json` 提供复活、满状态、治疗、休息、传送、入口、发放／新增物品、删除配置／角色、开场、重开、撤销、揭示和复核等步骤。先查实际对象、当前值和规则；有实质歧义才提供方案选择，已明确的要求直接生成待审核指令。

例如“复活”需要同时检查生命、力量、失能和状态卡，不能只补生命或反复调用不允许死亡角色使用的休息规则。角色搜索标注实际绑定的玩家账号；执行前仍复核实例的模板、所属玩家和活动状态。首次批准角色的 `sv.profile` 不能用来复活已有角色。实际完成以命令回执为准。更新后重启房间加载新模块与作者声明；网页玩家资源需重新导出。

“钱币／金钱／财富”明确映射到角色 `numbers.pips`。读当前值后通过受审 `entity.update` 调整，仅改变所需字段，并附给该角色 owner 的通知；不把钱币当背包物品，也不再询问已知字段含义。`sv.world` 只处理场次开场／回合／结束，不能猜造 `addPips` 等 operation。历史短确认继承已确定意图，已过时数值与空槽必须重查。

新AI宿主批次将支持范围内的修改和定向通知一并暂存，技术失败时整批不提交；提交后重试原请求不会重复发放或通知。旧的部分完成回执仍按原记录对账，不能重做已成功的修改或宣称已整批撤销。普通包侧Job保留未完成通知步骤，以原行动恢复；具体事务边界见[调试说明](ai-debugging.md#快捷取证)。
